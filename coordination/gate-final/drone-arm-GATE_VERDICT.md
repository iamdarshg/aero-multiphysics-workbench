### The CAN net_conflict — a real defect, not noise

14 of the 20 `net_conflict` entries are cosmetic (`/` vs `{slash}` in autogenerated pin names). **Two are real:**

```
Pad net (/CANH) doesn't match net given by schematic (/CAN interface/U50_CANL).
Pad net (/CANL) doesn't match net given by schematic (/CAN interface/U50_CANH).
```

Evidence chain (all independent of the DRC tool):

1. **Device pinout (TI TCAN3413, SOIC-8):** the repo's own symbol `revb:TCAN3413` defines pin 6 = `CANL`, pin 7 = `CANH`. This matches the TI datasheet ordering for TCAN341x SOIC-8 (TXD, GND, VCC, RXD, VIO, CANL, CANH, STB).
2. **Schematic intent** (`kicad-cli sch export netlist`, net codes 41/42/47/48):
   - `/CAN interface/U50_CANH` → FL50 pin **1**, R122 pin 1, U50 pin **7**
   - `/CAN interface/U50_CANL` → FL50 pin **2**, R122 pin 2, U50 pin **6**
   - `/CANH` → FL50 pin **4**, D50 pin 1, J2 pin 3
   - `/CANL` → FL50 pin **3**, D50 pin 2, J2 pin 4
   → schematic windings are **{1,4} and {2,3}** (H→H, L→L).
3. **Board** (`FL50`, rotation 0°, 2×2 grid):
   - pad 1 = `U50_CANH`, pad 2 = `/CANH`  → column **{1,2} = H+H**
   - pad 3 = `U50_CANL`, pad 4 = `/CANL`  → column **{3,4} = L+L**

**The board pairs the choke by column; the schematic pairs it by diagonal.** If the real ACT45B pairs diagonally, the board connects `U50_CANH → /CANL` and `U50_CANL → /CANH` — a crossed differential pair.

**Why this matters — cannot be dismissed as a schematic typo alone:** the ESC board's `FL201` is the **same MPN** (`TDK ACT45B-110-2P-TL003`, same footprint). The ESC's own schematic is **widely different and self-consistent**:

```
ESC /CANH                   : FL201 pin 2, D202 pin 1, J702 pin 3
ESC /CANL                   : FL201 pin 4, D202 pin 2, J702 pin 4
ESC /Controller and ADC/U206_CANH : FL201 pin 1, R242 pin 1, U206 pin 7
ESC /Controller and ADC/U206_CANL : FL201 pin 3, R242 pin 2, U206 pin 6
```

ESC schematic pairs **{1,4} = H+H and {2,3} = L+L** — the **opposite** of the main board. The main board cannot be simultaneously right with two different conventions across two schematics of the same product. **One of them is wrong; the repo does not establish which.**

**Adjudication is BLOCKED:** the TDK ACT45B-110-2P-TL003 datasheet is **not in the repo**, and TDK, Mouser, Digi-Key and ComponentSearchEngine all return HTTP 403 from this host. The winding pin-pairing therefore **cannot be resolved from available evidence**. This is an open, unresolved electrical risk on the CAN bus.

### Is the 1 ERC warning actionable?

```
SHEET: /   severity: warning   type: lib_symbol_mismatch
  Symbol 'L_Coupled' doesn't match copy in library 'Device'
  item: Symbol FL50 [L_Coupled]
```

**Verdict: benign, not actionable as an electrical defect** — but it *is* a traceability smell.

- `L_Coupled` is a KiCad **stock** library symbol; the warning means the cached copy inside the schematic has drifted from the installed `Device` library.
- It is a **warning**, not an error; ERC otherwise reports 0 on the root sheet across all 7 sheets.
- It carries **no pin/net consequence** — the connectivity is fully defined by the netlist, which exported cleanly.
- **However:** it is on `FL50`, the very part whose pin pairing is in dispute. A stale, drifted symbol is a plausible contributing mechanism for the H/L discrepancy. It should be resolved (`Update Symbols from Library`) as part of closing the CAN blocker, not because it breaks netlist generation.

**Scope discipline honoured:** ERC was run **only on the root sheet** as a hierarchical design. The 37-violation standalone `rf_915.kicad_sch` run was **not** repeated and is **not** evidence of anything.

## DA-G2 — RF integrity

### Measured reference-plane attribution

**In1.Cu zone inventory** (from `main_rev_b.kicad_pcb`):

```
In1.Cu filled zones (priority order): [('/3V3', priority 1), ('/GND', priority 0)]
In2.Cu filled zones               : [('/1V1', priority 1)]
```

**In1 is `/3V3`, not GND.** In2 is `/1V1` — it has **no GND at all**. This is the structural root cause of the entire RF finding: on a 4-layer board with GND only on F.Cu/B.Cu, an In1-referenced trace sees a power plane.

**Attribution over RF copper** (point-in-filled-polygon, priority-ordered; 132 signal segments + 132 power/bias segments = 198 segments, 231.40 mm):

| power/bias/clock in RF area (150.9 mm) | 7,509 | 63.36 % | 0.45 % | 36.18 % |
| **all RF-area copper** (231.4 mm) | 11,700 | **69.23 %** | **0.29 %** | 30.48 % |

Length-weighted: signal **79.83 % /3V3, 0.00 % /GND, 20.17 % void**; combined **69.37 % /3V3, 0.29 % /GND, 30.33 % void**.

### CC_LNA_N / CC_LNA_P asymmetry — confirmed

```
/915 MHz RF/CC_LNA_N : 7 segments, 2 vias
    F.Cu   segments=5  length=3.463 mm
    In2.Cu segments=2  length=1.840 mm   (53% of its length on an inner layer)
/915 MHz RF/CC_LNA_P : 1 segment, 0 vias
    F.Cu   segments=1  length=4.938 mm   (stays on F.Cu)
```

Confirmed. `CC_LNA_N` is routed onto **In2.Cu**, whose only plane is **`/1V1`** — no GND whatsoever. Its partner stays on F.Cu. This is a return-path break plus intra-pair skew on a differential LNA connection. `CC_LNA_N` also measures **100 % over void on In1**, consistent with having been dropped off the outer layer.

### Impedance — quasi-static estimate (NOT a field solve)

`RF_50R` netclass (`main_rev_b.kicad_pro`): **track width 0.35 mm**, via 0.6/0.3 mm, clearance 0.125 mm. Confirmed on board: 70 segments at 0.35 mm.

**The project defines no stackup at all** — `board.design_settings.stackup` is an empty object. Dielectric height is therefore an **assumption**, not a design value.

Closed-form microstrip (`Z0 = 87/√(εr+1.41)·ln[5.98h/(0.8w+t)]`, w = 0.35 mm, t = 0.035 mm, εr = 4.35):

| h to In1 (mm) | Z0 (Ω) | w needed for 50 Ω |
|---|---|---|
| 0.10 | 23.2 | 0.144 |
| 0.15 | 37.9 | 0.239 |
| **0.20** | **48.4** | **0.333** |
| **0.21** | **50.1** | **0.351** |
| 0.25 | 56.5 | 0.427 |
| 0.30 | 63.1 | 0.521 |

**Reading:** at a common 4-layer spacing of h ≈ 0.21 mm to In1, **0.35 mm is exactly the 50 Ω width** (50.1 Ω). So the **width itself is defensible** and must *not* be reported as wrong. The defect is that **the stackup is undefined**, so the width is unverifiable against a real fabricator. If the board house delivers h = 0.15 mm, Z0 falls to 37.9 Ω (−24 %); if h = 0.30 mm, it rises to 63.1 Ω (+26 %). A ±26 % impedance swing is available purely by stackup choice.

**Explicit scope statement:** this is a **quasi-static closed-form estimate**. It is **not** an electromagnetic field solve, **not** an S-parameter extraction, and assumes a solid reference plane at height h — which, per the measurement above, **does not exist here** (the "reference" is `/3V3`, with 30 % void and 0 % GND). The true impedance of these traces is **unknown and unmeasurable on this host**.

### DA-G2 verdict: **PARTIAL**

Reference-plane finding **reproduced** (and corrected in magnitude). Impedance **cannot be certified**: quasi-static estimate only, on an undefined stackup, over a non-GND reference plane. DA-G2 requires *"no unsupported layers; impedance note"* — the layers are **not** supportable (In2 = /1V1 only) and the impedance has no fabricator stackup behind it.

## 8. Decision: Can this board be called fab-ready?

**No. This board cannot be called fab-ready, and the gap is not marginal.**

The order below is by severity, most blocking first.

1. **There is no usable fabrication package.** The only Gerber set in the repo (`hardware/main/pcb-gerbers-1/`) was generated **2026-03-31** against a board now dated **2026-11-11**, stamps its revision as `rev?`, gives **all 11 layers the same 288.40 × 204.24 mm extent while the real board is 140 × 100 mm**, and matches **0 of 11** freshly exported layers. Handing this to a board house produces a different board. This alone is disqualifying and is fully in the project's power to fix.
2. **The fabrication contract is empty.** No stackup is defined in `main_rev_b.kicad_pro` while the `.gbrjob` declares `"ImpedanceControlled": true` and `"Finish": "None"`. A fab house cannot build impedance-controlled copper from no impedance definition. No DRC receipt, no pick-and-place, and no SHA-256 manifest tied to the board hash exist — three of the four things DA-G4 explicitly requires.
3. **The ESC control interface is physically incomplete.** J60–J65 exist in the schematic, are absent from the board, and are absent from the BOM. `PWM_ESC1..6` (U10 pads 43–48) terminate in autogenerated unconnected nets. This is a **drone** arm board whose six ESC outputs can be neither connected nor populated. DRC's "0 unconnected" is an artefact of the connectors having been deleted, not evidence of a complete netlist.
4. **The CAN differential winding pairing is unresolved and self-contradictory.** The main board pairs FL50 by column {1,2}/{3,4}; the main schematic pairs it by diagonal {1,4}/{2,3}; the ESC board's identical-MPN FL201 follows the diagonal convention. The two schematics in this repo cannot both be right, and the TDK ACT45B-110-2P-TL003 datasheet needed to settle it is unobtainable. Shipping a possibly-crossed CAN pair is a board-spin-level risk, and the stale `L_Coupled` symbol behind the single ERC warning is a plausible contributing mechanism.
5. **The RF path has no real reference plane and its impedance is uncertified.** In1 is `/3V3`, In2 is `/1V1`. Measured over the RF-area copper: **0.29 % over GND**, 69.2 % over `/3V3`, 30.5 % over voids. `CC_LNA_N` is split across F.Cu and In2.Cu (a plane with no GND) while `CC_LNA_P` stays on F.Cu. The 0.35 mm `RF_50R` width is *plausibly* 50 Ω — but only if the undefined stackup happens to be ≈0.21 mm to In1; at 0.15 mm it is 37.9 Ω, at 0.30 mm it is 63.1 Ω. That ±26 % swing is uncontrolled.
6. **There is no simulation and no measurement, and none can be produced here** (DA-G5, DA-G6 BLOCKED — no solver, no VNA, no VISA). So items 5 and the actual RF performance are **unverifiable by any means currently available**, not merely unverified.

**The honest one-line answer:** the routing is electrically plausible and DRC-clean on its own terms, and the repo's own `RELEASE_STATUS.md` already states the board is *"not fabrication-ready pending board-house confirmation of stack-up, microvia/via-in-pad processing, RF impedance, and manufacturing tolerances"* — this audit finds that assessment **correct, and understated**, because it does not mention the stale Gerbers, the missing ESC connectors, or the unresolved CAN pairing. A defensible path forward is: define and get a quoted stackup → regenerate and hash-lock the fab package → restore J60–J65 and their BOM lines → resolve the FL50 winding pairing against a real datasheet → re-run DRC with `--schematic-parity` to zero → only then order first articles, and treat all RF claims as open until a VNA touches the board.
